# Agent harness: how we build, and how the product's agent should work

_Research note, Fri 13 Nov. Distilled from a private reading list of public articles; ideas restated in our own words. Sources at the end. **(?)** = uncertain or single-source._

**The one idea:** verification has to come from outside the model. Five parties who disagree about almost everything else (OpenAI, Anthropic, Hashimoto, Böckeler, Horthy) agree on this. A model checking its own work without an oracle doesn't help and sometimes makes things worse (Huang et al. 2023). Everything below follows from it.

## A. For how we build (coding agents, ~36 h)

1. **CLAUDE.md is a map, not a manual.** OpenAI's single big AGENTS.md failed: context is scarce, too much guidance stops being guidance, and the file goes stale at once. Keep the root file at about 100 lines that point into `docs/`. Spend the lines on **gotchas** (pack units, the 1,000-product API cap, no bulk API sweeps, `$state.raw`). Leave out generic advice and ALL-CAPS warnings.
2. **What the agent can't see doesn't exist.** Decisions made in chat are invisible to a lane. Put each one in the brief, DECISIONS, or a type in `core/`. Keep briefs to three parts: **task, guardrails, exit criterion**. Don't script the steps; Cherny reports that over-specified step lists now hurt.
3. **Every lane needs an oracle it can run alone.** Use the per-lane dev port, `pnpm check`, and a Playwright screenshot of the lane's route as its acceptance check. OpenAI boots the app per worktree and gives the agent DOM snapshots, screenshots and logs. That makes "make it fast" or "make it look right" something the agent can check. Our fixture adapters are the oracle for every port.
4. **Turn invariants into checks, not review comments.** Böckeler calls these computational sensors: deterministic and fast enough to run on every change. Tonight: a lint rule that bans Svelte, DOM and SDK imports in `src/lib/core/`; a test that every state change goes through `applyOps`; a test that every port has a fixture. **Write lint messages as fix instructions.** The agent reads the message, so it is a prompt you control.
5. **Pair guides with sensors.** Guides alone give rules nobody checks. Sensors alone let the agent repeat the same mistake. When one mistake shows up in two lanes, add one line to the rulebook or a lint rule, then regenerate. Don't hand-patch each lane ("fix the loop, not the code").
6. **Parallel reads, serial writes.** Cognition and Anthropic agree on this split. Fan out research, review and tests freely. Code writes go one lane at a time per worktree, with owned paths and lead-only merges, as we already do. Unstructured agent swarms are "mostly a distraction"; the shape that works is a manager that splits the work, children that do it, and a manager that merges.
7. **Review with a clean context.** Cognition finds that a review agent catches more when it shares *no* context with the coding agent: it reads only the diff and works backward. Before each merge, run a fresh reviewer on the lane diff. Give it a short rulebook (CLAUDE.md hard rules plus the brief) and have it cite a rule for every finding. A reviewer that only gives opinions (an LLM grading code with no rulebook) is noise.
8. **Vertical slices, small diffs.** Models like to plan horizontally: schema, then service, then API, then UI. Make them build one path end to end: contract with mock data, then UI on the mock, then the real adapter, then error handling. Read 100–200 lines at a time instead of 2,000. Horthy's line: 30 minutes of planning saves hours of review.
9. **What kills agent "software factories":** taking the human review out entirely ("lights-off"); agents copying bad patterns already in the repo (assume everything you merge becomes the template); stale instructions; and parallel writers on shared files. Hackathon fixes: the lead reads every merge, a slop sweep at each integration, a STATUS rewrite at each checkpoint, contracts frozen before fan-out.
10. **Human attention is the scarce resource, not tokens.** Hashimoto turns off agent notifications and chooses when to check in. Batch integration every ~90 min, and let lanes report in their briefs, not in chat.

## B. For the product's agent (kitchen purchasing agent)

1. **Start with a workflow, not open agency.** Anthropic (_Building Effective Agents_): prefer fixed code paths around model calls, and only add autonomy where they fail. Our flow is Request → Lookup → Order → Approval. Code it as fixed steps where the model ranks, explains and asks. A goal-driven loop with no outside stopping rule repeats AutoGPT's failure. Bound every loop with a step cap and a deterministic "done" check (order valid, under the limits).
2. **Orchestrator-worker for reads only.** Anthropic's research system uses a lead that plans, workers that search in parallel, and the lead that synthesises. It beat a single agent by 90% on their eval, at roughly 15× the tokens. For us, fan out lookups (one worker per anomaly or substitute candidate), but writes to the plan go through one `applyOps` path. Workers should write results to the store and return **ids**, not full payloads ("artifact passing"); that avoids information getting lost as it is passed along.
3. **Scale effort explicitly.** Early agents spawned 50 subagents for simple queries. Put rules in the prompt: a routine reorder is 1 agent with a few tool calls; a single anomaly gets a few workers; an event like the Christmas dinner gets a planned fan-out.
4. **Tool design is the interface (MCP).** Give each tool one distinct purpose and a clear description. Put usage guidance in the tool description, not the system prompt. Prefer expressive types (enums for tier `act|propose|signoff`, units, temperature class) over examples. Anthropic had an agent use flawed tools and rewrite their descriptions; reported result: 40% faster tasks **(?)** (no baseline given). Cheap version for us: run the swarm against our MCP and read where it stumbles.
5. **Make the MCP server teach the domain, not just wrap the API.** An MCPCon talk, "Most MCP Servers are Empty", argued that the useful servers teach the domain. So expose `compare_by_priorities`, `get_substitutes` and `explain_line`, with pack-size and cut-off constraints in the results. Don't stop at `price` and `availability`. The 2026-07-28 MCP spec is stateless request/response, with state kept in explicit handles the model passes back. Our `order_id` or `plan_id` is that handle.
6. **Evals: small, early, end-state.** Start with ~20 real scenarios (Anthropic did). Grade the **final state** (the right lines, quantities, tier, under the limits) rather than each turn, because agents reach the same result by different paths. For free text ("why?" explanations), use one LLM judge call with a rubric (accurate, cites its source, complete, efficient) that returns a 0–1 score and a pass/fail. Keep human spot checks: they caught biases the automated evals missed. Don't trust vendor benchmark scores; OpenAI retired SWE-bench Verified over contamination.
7. **Guardrails come from code, not prompts.** No instruction defends against prompt injection; instructions are content too (Willison). Use the "lethal trifecta" test (private data + untrusted content + a way to send data out) and break one leg on purpose. Product descriptions and scraped manufacturer data are untrusted, so the context that reads them can't place orders. Sign-off thresholds come from the kitchen's mandate in code, and the agent can't argue them away. Show the approver the op itself as data, not the agent's summary of it (see [mcpcon.md](mcpcon.md)).
8. **A verifier with a clean context checks the plan.** Use the Cognition pattern on our own agent: a second model (Nemotron in the concept) sees only the proposed order plus the mandate and checks it. It never sees the planner's reasoning. Its findings go back through the planner, which keeps the user's instructions in mind. That is how the reported setup avoids loops and going out of scope.
9. **Traces are the debugging surface.** Anthropic needed full production tracing to see *why* agents missed obvious things: bad queries, bad sources or tool failures. Log model, tokens, latency, tool calls and **intent** on every op. Make agents resumable from the op log after a failure, not restarted. This is also the provenance trail the challenge asks for.
10. **Ecosystem standards:** MCP, AGENTS.md and goose were donated to the Linux Foundation's Agentic AI Foundation (Dec 2025). A2A (agent-to-agent) is also hosted there, so the standards are neutral, not one vendor's. MCP Apps (UI shipped inside the agent) and WebMCP (pages declaring their capabilities to agents; Chrome origin trial) are the emerging front end. Payments: the notes cover only x402 plus "proof of terms and consent" from one talk **(?)**; nothing on AP2/ACP. Saying "MCP + OpenAPI, A2A-ready" is safe. Don't claim payment rails.

## Top 5 to apply tonight
1. Trim CLAUDE.md and each lane brief to: map + gotchas + task / guardrails / exit check (a command or Playwright screenshot).
2. Add a lint rule for `core/` purity and a test that all state changes go through `applyOps`, with lint messages written as fix instructions.
3. Before every merge: a clean-context reviewer agent on the lane diff that must cite a rule per finding; the lead still reads the diff.
4. Write ~20 end-state eval scenarios (routine week, +80 covers, salmon out, recall, injection in a product description) against the fixture adapter. Run them on every integration.
5. Shape the MCP tools as domain verbs with enums and handles, and make sure the context that reads untrusted text has no path to `place_order`.
