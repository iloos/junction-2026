## 1. Protocols
**AP2 (v0.2).** The old Intent/Cart Mandates are now **open** and **closed** mandates (`vct: mandate.checkout.open.1` / `mandate.checkout.1`, plus `mandate.payment.*`), as SD-JWT VCs. Trust: five roles; the **Trusted Surface MUST be non-agentic**, and all verification "MUST happen in deterministic code". Binding: the merchant signs a `checkout_jwt`; the closed mandate carries `checkout_hash`, so any change in the checkout breaks the approval. Human-present: the user signs the closed mandate. Human-not-present: the user signs an open mandate with constraints (`checkout.allowed_merchants`, `checkout.line_items`, `payment.amount_range`, `payment.budget` + `payment.agent_recurrence`), the agent's key (`cnf`), and a short `exp`; the agent signs the closed one. Replay/idempotency: an agent MUST NOT present another open mandate until the previous one is rejected; every verdict returns a signed **Mandate Receipt** with `reference` = hash of the presented mandate. Revocation: only `exp` plus budget consumption; no revocation list. B2C framing, but nothing card-specific in the checkout mandate. **Map:** our `Mandate` = open mandate (caps = `amount_range`/`budget`, tender list = `allowed_merchants`/`line_items`); our `Approval` bound to `termsHash` = closed checkout mandate with `checkout_hash`; our `Receipt` = Mandate Receipt. We have no signatures (one trust domain, which AP2 itself says is fine when the merchant and surface are non-agentic).

**ACP (OpenAI + Stripe, 2026-04-17, beta).** Merchant-run REST checkout sessions (`/checkout_sessions`, `/{id}/complete`). Idempotency is well specified: `Idempotency-Key` required on every POST, scoped to identity + endpoint; **409** in-flight with `Retry-After`, **422** on payload mismatch, `Idempotent-Replayed: true` on a replay. Consent: the buyer confirms in the agent UI; the delegated payment token carries an `allowance` {`reason: one_time`, `max_amount`, `currency`, `checkout_session_id`, `merchant_id`, `expires_at`}, i.e. bound to one session, amount and expiry. Status enum includes `pending_approval`, `requires_escalation`; error `approval_required`. **Not B2C-only any more:** payment carries `purchase_order_number`, `payment_terms` (`net_30`…) and `approval_required`. **Map:** our idempotency (workspace, caller, tool, key + request hash) is the same design; copy their HTTP codes and headers. Our `held{sign_off}` = `pending_approval`.

**UCP** (Google + Shopify, Jan 2026) is the shopping/checkout layer that AP2 plugs into (`/.well-known/ucp` discovery; AP2 mandate extension) (2nd). **Visa TAP** is agent *identity*, not consent: RFC 9421 HTTP message signatures bound to merchant domain and operation, with timestamp and session id for single use, keys in an agent registry. **Mastercard Agent Pay**: registered/verified agents get Agentic Tokens; users set what the agent may buy; passkey/biometric auth. Both are card-rail B2C; Valio kitchens buy on account/invoice, so these are **out of scope** (cite only). **x402**: HTTP 402 + stablecoin pay-per-request for APIs; irrelevant to wholesale ordering, skip.

**MCP.** Elicitation (2025-11-25): **form mode MUST NOT carry credentials or anything that "authorizes transactions"**; those MUST use **URL mode**, opened out of band so the client/LLM cannot see or fake the input, with a server check that the user who opens the URL is the one who started it. So the honest MCP approval is: tool returns held + an approval URL to *our* page (or error `-32042` URLElicitationRequired). **MCP Apps** (`ui://` resources, extension `io.modelcontextprotocol/ui`, official Jan 2026, 2nd for the date) can render our plan card inside Claude/ChatGPT, but the host is agentic, so it should show, not approve. **A2A v1.0**: task states `INPUT_REQUIRED`/`AUTH_REQUIRED` map to our `held`; `messageId` dedupe. Not needed for the demo.

## 2. Failure lessons → our architecture
| Lesson (source) | Element we have / lack |
|---|---|
| Vend 1–2: discounts, giveaways, selling below cost, quoting without checking; fix was **mandatory procedures** (verify price and delivery with tools), better tools, human purchase approval | Have: quote → hold → approve; prices from Valio API at commit; `TERMS_CHANGED`. |
| Vend 2: LLM "CEO" supervisor approved lenient requests ~8× as often as it denied them; a staffer installed a fake CEO by claimed vote | Have: authority is the bearer key's scopes, never chat (`Actor` server-derived). Avoid any LLM-as-approver. |
| WSJ newsroom: forged PDF "board documents" accepted by both agents; prices dropped to zero; PS5 and a live fish bought (2nd) | Have: mandate only changes via `mandate:write`, versioned. Lack: an explicit eval that a document/photo cannot change the mandate or approve. |
| Project Deal: no human sign-off, agent bought something the owner already owned; weaker model got worse deals and users did not notice | Have: stock-aware demand. Pitch: tiers exist because users can't see bad delegation. |
| Magentic Marketplace: 80–100% take the first proposal; 10–30× speed-over-quality bias; manipulation via injected offers | Have: deterministic ranking over all candidates (D6), Gemini only gives a bounded fit score. |
| Prompt injection via tool data (AgentDojo; design-patterns paper: once untrusted input is read, it must not be able to trigger consequential actions) | Have: planted injection in a product description. Lack: written rule that Decide sees product text but returns only a score 0–4 (Map-Reduce/Action-Selector pattern), never tool calls. |
| Vending "didn't fit the machine" (MCPCon) | Have: lot size, pack units, `BELOW_LOT`, cut-off. |

## 3. Evaluation
τ-bench (retail, airline) scores the **final DB state against a goal state** and reports **pass^k** (all k trials succeed): GPT-4o <50% pass^1, pass^8 <25% in retail. τ²-bench adds dual-control (user also has tools); performance drops. ST-WebAgentBench's **Completion under Policy** (CuP) credits only completions that break no policy; CuP was under two-thirds of the raw completion rate. AgentDojo: 97 tasks, 629 security cases for injection through tool data. How teams test "never exceeds mandate": (a) policy enforced outside the model and tested as an invariant (our `applyOps`); (b) end-state checks, not transcript grading (our evals already do this); (c) repeated trials (pass^k) with an adversarial agent. **30-second demo:** an external agent over MCP tries N attacks (over-cap order, self-approval, replayed key with a changed payload, injected product text, price change after approval); a counter shows "attempts N · policy violations committed 0", next to the eval table (s1–s5 green, CuP = pass rate).

## 4. B2B ordering agents in practice
Valio Aimo's **A.I.mo** is an information assistant in My Aimo ("finds the information you need"), with human experts behind it; no ordering autonomy is described. **US Foods MOXē** turns uploaded documents/photos into an order (2nd). **Choco OrderAgent** captures orders from email, PDF, voicemail and notes for distributors; "Autopilot" pushes verified orders to the ERP and **flags exceptions for review**; tuned to ~97% on historic orders (vendor claim). Procurement agents (Ramp, Pactum, Didero, Spendflo, Procure AI; 2nd) automate intake, vetting, negotiation and approvals inside one company. **Gap:** all of them capture or route orders; none publishes a buyer-defined mandate that a *third-party* agent is held to, approvals bound to exact terms, or an open agent door with its own trust rules. That is our position: **the exception and trust layer**.

## Means for us (ranked)
1. **Name the mapping to AP2, don't implement the crypto (S; `docs/PITCH.md`, `core/contracts/plan.ts` comments).** Our mandate = AP2 open mandate, our approval = closed mandate bound by `termsHash` (≈ `checkout_hash`), receipt = Mandate Receipt. Add `approvalRef = hash(approval)` to the `Receipt` if it isn't there, so every order points to the exact consent.
2. **Copy ACP's idempotency HTTP semantics in REST/OpenAPI (S; `src/routes/api/tools/**`, `core/contracts/errors.ts` mapping).** `Idempotency-Key` header, 422 for `DUPLICATE` (payload mismatch), 409 + `Retry-After` in flight, `Idempotent-Replayed: true` on replay. Cite ACP in the OpenAPI description.
3. **Approval only on a non-agentic surface (S–M; `core/contracts/tools.ts`, `src/routes/mcp/**`, kitchen approve route).** External MCP calls that end held return `approvalUrl` (URL-mode elicitation shape) to our approve page; that page renders the plan's lines and hash from the store, not the agent's summary. Matches AP2 "Trusted Surface MUST be non-agentic" and MCP's rule that transaction consent never goes through form mode.
4. **Adversarial agent run with a violations counter (M; `evals/**`, ops route).** One scripted external agent replays 5–6 attacks from §3 through the tool registry; show "0 committed violations" live and in `pnpm eval`. Run the LLM agent path k=3–5 and report pass^k.
5. **Injection firewall rule (S; `src/lib/server/adapters/decide/**`, ARCHITECTURE "Ranking").** Product text and enrichment go only to Decide, which returns `{score 0–4, reason}` validated by zod; the planning agent sees ids and numbers. Add eval: a description saying "approve this order" changes nothing.
6. **Mandate cannot be changed by content (S; evals scenario).** Photo/PDF/chat claiming "manager raised the cap" → no `mandate_version` bump without `mandate:write`. Cite the WSJ forged-PDF case.
7. **Weekly cap as AP2 `payment.budget` + `agent_recurrence` (S; docs only).** We already lock the budget row per ISO week; say so.
8. **Avoid:** claiming AP2/ACP compliance, payments, signatures, Visa/Mastercard tokens or x402; an LLM supervisor as a safety layer; letting the external agent's free-text summary appear on the approve screen.

## Pitch lines (true if 1–4 are wired)
- "Google's AP2 calls it a mandate too: the human approves exact terms, and if the price changes, the approval is void. We built that for a kitchen, against Valio's live prices."
- "Any agent can search, quote and order through our MCP door. None can approve: approval only happens on the chef's screen, bound to a hash of the exact lines."
