## 1. Catalogue enrichment batch (17.5k products, from the local files only)
**Data in.** Split locally into ~90 JSONL shards of 200 products, run `modal volume put junc26-data data/valio/shards /valio` once (87 MB), then `fn.map(range(n_shards))`. Shards on a Volume beat passing chunks: they're uploaded once, reruns are free, and inputs stay tiny. Passing 1 MB chunks through `.map` also works and is the fallback.
**Three stages, all in one `modal run jobs/modal/enrich.py`:**
1. **Rules (CPU, chunked map):** pack size (netWeight with its packaging level, plus a name regex for "4x5 kg", "60 g x 90 / 5,4 kg" and "70cl"), allergens and labels from `classifications`, an `isFood` guess from category, and a carbon **prior** (the category median over the 11k known values). 17.5k products in about 1 minute, under $0.01.
2. **LLM (GPU), only for products with a gap or a conflict, about 11k:** one structured-JSON call per product does everything: pick the pack size (with its level) when sources disagree, estimate carbon from the prior and the ingredients (beef share, dairy fat), and flag diet attributes (vegan, lactose-free, gluten-free) where the classification is empty. The input is the name, ingredients, category, label list and prior; the output is `{value, unit, method, confidence, why}` per field. Run **Gemma on Modal**: either `modal endpoint create --model google/gemma-4-E4B-it` (a Dedicated Endpoint with an OpenAI-compatible `/v1/chat/completions`, a proxy-token bearer, and `--min-containers 0 --max-containers 4`) or our own vLLM `@app.cls(gpu="L40S")`. The model library also lists `Nemotron-3.5-Lightning-30B-A3B`, `Nemotron-3.5-Super-VL-120B` and `Qwen3-Embedding-0.6B/8B`. Calls go from a CPU map with `@modal.concurrent(max_inputs=32)` so vLLM can batch. **Featherless can't take this load:** its plans cap concurrency at 4 units (Chat) up to ~100 (API tier), and models cost several units each, so 11k calls would take hours.
3. **Embeddings (GPU):** `Qwen3-Embedding-0.6B` (1024-d) via the endpoint's `/v1/embeddings`, or sentence-transformers in `@app.cls(gpu="L4")` with `@modal.enter` loading the model and `@modal.batched`. 17.5k × ~300 tokens is 5M tokens: minutes on one L4.

**Cost and time (estimates; only the CPU numbers are measured):** about 9M input and 1.7M output tokens. At ~3k output tok/s per L40S ($1.95/h), 4 GPUs take ~5–10 min plus 2–4 min of cold start, about **$1–2**. Embeddings cost ~$0.10. **Total < $3 and ~15 min wall time.** Rates: CPU $0.0000131/core-s, L4 $0.80/h, L40S $1.95/h, H100 $3.95/h. Sandboxes cost 3× the CPU rate.
**Results out:** each shard **upserts straight into Aiven Postgres** (Modal Secret `junc26-db` holding `DATABASE_URL`) and fires `NOTIFY enrichment`, so the control room's coverage bars climb live. Each shard also writes JSONL to the Volume. `modal volume get` then pulls the JSONL into the fixture (`data/enriched/catalog.jsonl`, seeding PGlite), so the demo survives without Modal. Every filled value carries provenance: `measured` (Valio), `rule:<name>`, `estimated:category-median`, or `llm:<model>@<runId>` with its confidence. Use `return_exceptions=True` and rerun only the failed shards.

## 2. Swarm runner (500 kitchens against OUR simulator)
- `run_kitchen(spec)` is an **async** Modal function with `@modal.concurrent(max_inputs=50)` and `max_containers=20`. Each agent is I/O-bound (HTTP to the simulator and the LLM), so 500 agents fit in ~10–20 containers, under the **Starter plan's 100-container cap**. The app starts a run by calling the deployed `start_swarm` through the JS SDK (`modal.functions.fromName("junc26-swarm","start_swarm")`, then `.spawn(...)`). `start_swarm` fans out with `.spawn_map` (fire and forget; it can't return results yet) or `.map`.
- **Loop:** at most 8 steps (repo rule). The tools are HTTP calls to the app's simulator (`/sim/api/availability`, `/sim/api/price`) and our order API. Each kitchen has a persona (priorities, a mandate, one planted anomaly). About 400 kitchens run a scripted policy and **~100 use the LLM**, so cost and latency stay predictable and the scripted path doubles as the fixture.
- **Events:** each step POSTs `SwarmEvent` to `/api/swarm/events` with an `X-Swarm-Token` header (from the `junc26-app` Modal Secret). Buffer per container and flush every 500 ms. 500 agents × 8 steps over ~3 min is ~25 req/s. At the 10× stress (5,000 agents) batching is mandatory. Each event carries `MODAL_TASK_ID`, so the control room can count live containers itself.
- **Cost:** CPU ~20 containers × 5 min, about $0.05. LLM: 100 agents × ~5 calls × ~1.5k tokens, on the same Gemma endpoint, under $0.50. **Prewarm the GPU 10 min before the pitch** (`min_containers=1`, then reset to 0).

## 3. Sandboxes for agent-written analysis code: feasible, about 2 h
Tested from Node (above). The shape: `src/lib/server/` adapter behind `CodeRunPort.run({code, datasetIds}) → {stdout, files, ms}`. It calls `apps.fromName(.., {createIfMissing:true})`, then `sandboxes.create(app, image, {blockNetwork:true, cpu:1, memoryMiB:1024, timeoutMs, idleTimeoutMs, volumes})`, then `filesystem.writeText(code)`, `exec(["python", ...], {timeoutMs})`, `stdout.readText()` and `terminate()`. Use a **prebuilt image with pandas** (build it once, because the first build takes 20+ s) and **mount the data snapshot as a Volume** (`volumes.fromName`) rather than writing it in, since writeText ran at ~0.5 MB/s. `outboundDomainAllowlist` also exists if code needs one API. Constraints: gRPC (nice-grpc) means it needs the **Node runtime, not edge**. Auth comes from `MODAL_TOKEN_ID` / `MODAL_TOKEN_SECRET` in server env. The fixture returns canned outputs for the 3 demo questions. Cost: 1 core × 10 s ≈ $0.0004 per run. The risky part of those 2 h is code-generation quality, not Modal: ~1 h of plumbing, ~1 h of prompt and UI.

## 4. Web endpoints: keep the Valio simulator in SvelteKit
`@modal.fastapi_endpoint()` / `@modal.asgi_app()` (+ `@modal.concurrent`) give a public `https://<ws>--<app>-<fn>.modal.run` in minutes, with a few seconds of cold start and a **200 req/s default per function** (429 above that). Still, the simulator belongs **in our app**. Its stock is **shared state**: 500 kitchens draining the salmon is the point, and that state lives next to orders in Postgres. It is also the same TS code as the `ValioPort` fixture adapter, while a Python copy on Modal would fork the core. Reopen this if the app host can't take ~250 req/s at the 10× stress. Endpoints that are worth it: the Gemma/embedding endpoint (§1) and, optionally, a `trigger` fastapi endpoint if the JS SDK misbehaves on the host.

## 5. What scores "Best use of Modal", and what to show
- **Effective use (40):** Modal does four distinct heavy jobs: a CPU fan-out, **our own GPU inference** (Gemma plus embeddings), a 500-agent concurrent swarm, and Sandboxes. Nothing on Modal is a wrapper we could run on a laptop.
- **Ambition (25):** the whole catalogue enriched with provenance in ~15 min, 500 agents (and a 5,000 stress run), and model serving we host ourselves.
- **Impact (20):** it fills exactly the gaps Valio named (carbon, pack sizes, missing specs). The swarm is a **trust stress test**: how many lines were acted, proposed or signed off, which policy breaches were caught, and the injection attempt that was blocked.
- **Demo (15):** a "Run swarm (500)" button in the deployed control room. On screen: a 500-dot grid that changes state, events/s, **live containers** (from `MODAL_TASK_ID`), a running cost estimate, and coverage bars (carbon 63% → 100%, split into measured and estimated), with the Modal dashboard's container graph alongside. A recorded run is the fallback. The write-up includes the `modal billing report` numbers.

## Decisions for ARCHITECTURE
1. **`jobs/modal/`** is a uv Python project, separate from `src/`, with three apps: `junc26-enrich` (`enrich.py`), `junc26-swarm` (`swarm.py`: `start_swarm`, `run_kitchen`) and `junc26-llm` (vLLM Gemma + embeddings, or `modal endpoint create`). Deploy with `modal deploy`. A schema-only Python mirror of the TS types; no business logic in Python except enrichment rules.
2. **Contracts:** `EnrichedField {productId, field, value, unit, provenance{method, model?, source?, confidence, runId}}`, a Postgres table plus `data/enriched/catalog.jsonl`. `SwarmEvent {runId, kitchenId, step, type, payload, ts, containerId}`, POSTed in batches to `/api/swarm/events`. `CodeRunPort` with a Modal adapter and a fixture.
3. **App ↔ Modal:** the app holds `MODAL_TOKEN_ID/SECRET` server-side and uses the JS SDK for `start_swarm.spawn` and Sandboxes. Modal holds Secrets `junc26-db`, `junc26-app` (`APP_URL`, `SWARM_TOKEN`) and `junc26-llm` (endpoint URL + proxy token), created with `modal secret create`, never committed.
4. The simulator stays in SvelteKit (§4). The LLM for the swarm and the batch is Gemma on Modal; Featherless/Verda serve single interactive calls.
