# Ring 3 review: code coherence, wiring, maintainability

_Independent reviewer, Sat 14 Nov evening, main at `1922679`. Read-only. `pnpm check`: 0 errors, 0 warnings (6176 files)._

## Verdict
1. The core holds: approval binding (version + termsHash + plan termsHash, orders.ts:359-366), one `transact` → `applyOps` write path, a seq-validated bounded state cache, and one tool gate (`serveTool`) for REST/MCP/kitchen. Good shape for a 7-session build.
2. The seams are in **ambient scope**. Two AsyncLocalStorages (`inWorkspace` for clock/overlay, `withExternalScope` for spend/trace) are entered by different callers, and every path that misses one runs on the stage's clock or escapes the per-key cap. Four entry points miss one.
3. One real cross-door bug: tasks born on /request (`t-<planId>`) can't be restored or continued by the chat dock (`/^task-/` guard).
4. Two "next action" models disagree on cut-off-passed lines (core says find a substitute; the agent rule says change the date).
5. Cleanup before freeze is cheap: ~1k lines of test-only or dead code in prod paths, and about 30 historical or lane-named comments.

## Findings (ranked)

### High
**H1. Chat can't continue a task that /request or a menu plan created.** _Verified._ `request/task.ts:51` mints `t-${plan.id}`. `chat/turn.ts:86` mints `task-…`. Both chat routes accept only `/^task-[\w-]{1,60}$/` (`api/chat/turn/+server.ts:37`, `api/chat/task/+server.ts:20`). The turn joins the request's task by planId (`turn.ts:205-209`) and emits `taskId: 't-…'`. ChatDock remembers it and sends only `taskId` next (ChatDock.svelte:130). The route silently drops it, so a `continue` turn fails with "Say what you need", and a restore gets **400**. **Why it matters:** the demo path "/request → open in Kitchen → chat continues" breaks. **Fix:** one id helper in `contracts/task.ts` (`taskIdFor(planId)` / `newTaskId()`) with one shared regex, and relax both routes to `/^(task|t)-[\w:.-]{1,62}$/`. Add a test that joins a request task through chat. **Size:** S. **Owner:** B + E (lead for the contract).

**H2. Chat turns bypass the external scope: Gemini Decide spend there is uncapped per key and missing from the trace drawer.** _Verified wiring; impact inferred._ `api/chat/turn/+server.ts:56` and `api/chat/task/+server.ts:27` pass `realHandlers()`, the raw handlers. Only the exported `handlers` (`tools/handlers.ts:126-141`, `lazyReal`) wraps calls in `withExternalScope(scopeFor(ctx))`. Without a scope, the Decide guard key is `null` (`adapters/decide/index.ts:214`), which means the global cap only (`external/ledger.ts:61-69`), and traces go to `noTrace`. The same applies to `ops/views/+server.ts:26`, `tasks/server.ts:12` and `demo/reset.ts:16`. **Why:** one chatty visitor can drain the global Decide cap for everyone, and chat's model decisions never show in the Why/trace view that D11 sells. **Fix:** chat routes use `handlers` (lazyReal), not `realHandlers()`. Better: make `realHandlers` private and export only the wrapped set. **Size:** S. **Owner:** E (chat), lead (handlers.ts).

**H3. Two next-action rules disagree on a cut-off-passed line.** _Verified._ Core `LineView.nextAction` puts `cutoff_passed` in `SUPPLY` → `'find_substitute'` (`core/mandate/view.ts:30-37`, `:82`), and `asOf` does the same (`core/services/views.ts:126-131`). `agent/next-action.ts:64-68,99-105` says the opposite ("pick a later delivery date (the product is not the problem)"). Its header claims the kinds match core's read model "where they meet ('change_date')" (`next-action.ts:16`), but core has no `change_date` (`contracts/plan.ts:178-186`). Also, an eligible line that `asOf` closes (`committable:false`, state still `eligible`, no `cutoff_passed` reason) is neither `late` nor `eligible` in `nextActionFor`, so the plan can read "Nothing is open" while its line view says find a substitute. **Why:** Why-chain/Kitchen (line view) and MCP meta/ledger/chat (plan rule) give a chef opposite advice on the same line. **Fix:** add `'change_date'` to `LineView.nextAction`, map `cutoff_passed` to it in both core spots, and have `nextActionFor` count `view.blockedReason?.code === 'cutoff_passed'` as late. Move `nextActionFor` into `core/mandate/` (it is pure and only imports contracts). **Size:** M. **Owner:** 8d + E.

### Medium
**M1. `/api/agent/run` builds its context outside the workspace scope.** _Verified._ `runRoutineAgent` → `serverContextSource().today/now` reads `b.ports.clock` (`agent/index.ts:129-140`) with no `inWorkspace`. The clock falls back to the configured workspace (`store/db-ports.ts:66`, `scopedWorkspace() ?? workspaceId`), which is the stage run's clock and not the key's sandbox. `buildContext` also reads plans for `principal.runId` (`agent/context.ts:99`), which `resolveRequest` set synchronously (`auth/index.ts:88`) before any `ensureRunLoaded`. **Fix:** wrap `runGoal` in `inScope(principal.workspaceId, …)` (export `inScope` from a neutral module, e.g. `demo/scope.ts`) and re-read the run first. **Size:** S. **Owner:** E.

**M2. Key-resolved contexts carry a stale `runId` after a restart: reads hit the old run, writes the new one.** _Verified mechanism._ `onCurrentRun` returns early when `hasRun` is true (`demo/reset.ts:113-117`). `/api/request` calls `inScope` → `ensureRunLoaded` first (`request/index.ts:63-66`), so by the time `serveTool` runs, `hasRun` is true and the ctx keeps `run-1`. Reads use `ctx.runId` (`store.load`, e.g. `get-context.ts:29`). Writes use the store's `runOf(ws)` = current run (`drizzle-store.ts:293`). Non-visitor rooms (`ws-judges`) are never corrected (`isVisitorWorkspace` gate). **Fix:** `onCurrentRun` always returns `{...ctx, runId: await ensureRunLoaded(ws)}` (it is memoised, with a 5 s refresh) for every non-memory workspace, unless `MANDATE_RUN` is set. **Size:** S. **Owner:** 9c.

**M3. `/api/web/*` routes run web tools outside `serveTool`.** _Verified._ The routes call `webTools(env)[x](w, …)` directly (e.g. `api/web/recall/+server.ts:30`) with `authed(…, 'web:recall')`. That 4th argument is a `via` label, not a scope (`web/route.ts:9-21`). The routes get no `inWorkspace`, no `onCurrentRun`, no output validation and no `meta`. `POST /api/web/recall {url}` writes `RecordAnomaly` ops into the caller's run (`web/ingest.ts:280`) for any key, including `job` (read-only). The spend key differs by door: the MCP/REST tool uses `ctx.actor.id` (`tools/handlers.ts:92`), the routes use `kind:id` (`web/index.ts:240`), so one key gets two daily buckets. **Fix:** route the three tool-shaped endpoints through `serveTool` (`lookup_facts`, `find_outside`, `check_recall`). Gate recall ingest on `plan` scope. Use `callerKey` in handlers.ts too. **Size:** M. **Owner:** D.

**M4. Menu flow timestamps outside the tool gate.** _Verified, low impact._ `/request/menu` now wraps in `inScope` (good). The same `menu/server.ts` functions have no scope of their own: `deps().now` and `taskForPlan(now)` read whatever scope the caller set (`menu/server.ts:31-38`, `flow.ts:280,308`). A future caller (chat, a job) would stamp reviews on the stage clock. **Fix:** move `inScope` inside `menu/server.ts` exports (and `request/index.ts` exports), not only in routes. **Size:** S. **Owner:** B.

**M5. Two copies of "today".** _Verified._ `agent/index.ts:136-137` hard-codes `Intl…'Europe/Helsinki'` next to `scenarioDate` (`core/scenario.ts:36`, `SCENARIO.timeZone`). `request/task.ts:11` `kitchenUrl` is a byte-for-byte copy of `tools/present.ts:18` `approvalUrl`. **Fix:** use `scenarioDate` and keep one URL builder (in core or `request/task.ts`). **Size:** S. **Owner:** E / B.

**M6. Server imports UI modules for domain logic.** _Verified._ `chat/turn.ts:28-30` and `tasks/ledger.ts:5` import `decisionsOf`/`decisionsDue` from `$lib/ui/decisions`. Request/menu import types and `format` from `$lib/ui/*` (12 files: `grep "from '\$lib/ui" src/lib/server`). `chat/turn.ts:30` imports a type from a `.svelte` file. One decision grouping is right; its home is wrong. **Fix (post-freeze):** move `decisions.ts`, `format.ts` and `request/types.ts` under `$lib/core` or `$lib/shared`, and re-export from ui. **Size:** M. **Owner:** lead.

**M7. GoalOutcome fallback contradicts D10.** _Verified._ `agent/outcome.ts:66-69`: without a FulfilmentView, "every line committed" → `confirmedNeeds` (supplier confirmed). D10 reserves that for receipt-backed quantities. **Fix:** without a view, committed lines count as `unconfirmedNeeds`. **Size:** S. **Owner:** E.
