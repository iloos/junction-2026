## 3. Conflicts and decisions needed
1. **Open requests: `/api/agent/run` (agt) vs a Plan step inside `/request` (req).** Options: build in agent path; build in request path; one service both call. **Ruling: one service.** `plan_event` accepts `{eventId} | {brief, dishes}`; a `menu` module (brief questions, Gemini proposal labelled estimate, KB lookup first) sits behind it; `/request` is the judge-facing UI (classify → questions as `AnswerSpec` chips → menu → plan), and the agent's new `requirements` intent calls the same tool. Why: R5 asks for one typed contract; agt is right that outcome/cancel/grants matter, and they come for free through the tool gate.
2. **Merge the two pipelines?** (agt: not before deadline; R5: one request contract.) **Ruling: don't merge; share modules.** The routine intent calls `parseRules` + `convert` from request for quantities and dates, and rejects what it can't honour. Why: fixes F4 without a rewrite.
3. **Shared vs per-judge sandbox.** Options: label it shared (R5-surf, 20 min); per-session run; per-visitor workspace (9c, 1f). **Ruling: per-visitor workspace** (`ws-j-<id>` from a cookie, lazily ensured; `MCP_KEYS` already takes `:workspace`), Ops opens the visitor's workspace by default, reset scoped to it; keep `ws-judges` as an explicit shared room by link. Why: peer review 10:30–14:00 is many concurrent QR visitors, and it fixes F2 in the same change.
4. **Prefer confirmed cover in ranking.** Options: weight; lexicographic tier; leave and label. **Ruling: lexicographic tier** (confirmed stock or make-in-house from confirmed ingredients > unknown supply), unknown candidates stay visible and labelled; record as D8 amending D6 ("missing values never score favourably" extends to supply). Why: D6 already says unknown never counts as cover; ranking it first contradicts that.
5. **Mixed commit audit: per-line authority vs split orders.** **Ruling: per-line authority** on `Order.lines[]` (`mandate | {approvalId}`), one order, one receipt. Why: split orders change the "retry → one receipt" semantics evals s1/s5 assert; per-line is additive.
6. **Decisions per reason (1f) vs one approval per plan (current).** Options: UI-only grouping; approval of a line subset per reason. **Ruling: subset approval** if `approve` can take `lineIds` within the pending terms (core to confirm, S); otherwise UI requires one confirm per reason group before the single grant. Why: an allergen change must never ride with routine lines.
7. **Submit Exa (and claim Context.dev "several endpoints")?** web: not unless a judge surface lands; D7: pursue. **Ruling: decide at the Sat 22:00 video checkpoint**: submit Exa only if a judge can type a product or question (UI or MCP `lookup_facts`) and see cited sources; otherwise leave the draft. Context.dev: submit with the monitor → hold story, claim one endpoint pair only. Why: drafts cost nothing; a weak sponsor demo costs pitch time.
8. **Hard limit on big events** (8d mild). **Ruling: keep**, add "split the order or raise the mandate" copy. Why: S, and the ceiling is a claim.
